# Switch web-sdk payload segments to deterministic i.v. nonce values

## Summary

Replace per-segment random AES-GCM IVs with the deterministic construction of NIST SP 800-38D
8.2.1: a random 8-byte fixed field, drawn once per stream, followed by a 4-byte big-endian
invocation counter.

## Problem / Motivation

The writer currently draws a random 96-bit AES-GCM IV for every segment. At high segment counts,
random IVs accumulate collision risk according to the birthday bound. Repeating an IV with the same
key catastrophically compromises AES-GCM confidentiality and integrity.

## Proposed Solution

Build each 96-bit IV as `fixedField || invocation`:

- The 8-byte fixed field is random, drawn once per `writeStream` call through the injected
  `CryptoService.randomBytes` so FIPS builds stay inside their boundary.
- Invocation 0 encrypts the key access object metadata; invocations 1, 2, 3 and so on encrypt
  payload segments in stream order. The writer refuses to issue an IV at or beyond 2^32.

Drawing the fixed field per stream rather than per key is what makes the scheme safe: `keyMiddleware`
is a public option, so a caller may hand the same `KeyInfo` to two `encrypt` calls. A constant fixed
field -- including the all-zero one -- would then repeat the entire IV sequence, metadata included,
under an identical key.

Calculate AES-GCM segment overhead directly instead of encrypting and discarding a dummy segment.
A cipher-level test and a write-time assertion keep `encryptedPayloadSize` honest in the probe's
place.

## Inputs / Outputs / Contracts

No public API or manifest schema changes. Each encrypted payload segment continues to store its
12-byte IV before the ciphertext and 16-byte authentication tag, and `method.iv` continues to hold
the metadata IV.

Deliberate divergence from java-sdk#393, which uses an all-zero fixed field. The two are wire
compatible -- readers take each segment's IV from its own prefix and never recompute it -- so this
is a writer-side hardening choice, not a format change. Worth raising with the BaseTDF spec owners.

## Edge Cases & Constraints

- Reusing a payload key across TDFs is safe for IV uniqueness, because each stream draws a fresh
  fixed field. It still means one key compromise exposes every TDF that shared it.
- Metadata uses invocation 0 of the same fixed field, because its split key is identical to the
  payload key for a single split.
- All key access objects in one manifest share the metadata IV, as they already share the metadata
  plaintext they encrypt.
- Carry propagates within the 32-bit invocation field only; the fixed field never changes.
- Empty payloads do not consume a payload IV.

## Out of Scope

- Changing the BaseTDF wire format or validating deterministic IVs while reading.
- Non-payload AES-GCM operations such as EC/ML-KEM key wrapping, which use different keys.
- Random-access or distributed segment writers; the web SDK writer emits segments sequentially.
- Rejecting manifests whose segment sizes are JSON strings rather than numbers. Such TDFs exist and
  decrypt today; the new size cross-check skips them rather than newly failing them.

## Acceptance Criteria

- [x] Every stream draws a fresh random fixed field through the injected crypto service.
- [x] Metadata encryption uses invocation 0 and payload segments begin at invocation 1.
- [x] Consecutive payload segments use consecutive invocations under one fixed field.
- [x] Two encrypts sharing a `KeyInfo` produce disjoint IVs, covered by regression test.
- [x] Counter carry and the 2^32 invocation ceiling are unit tested.
- [x] Segment-size calculation does not perform a throwaway encryption, and a cipher-level test
      plus a write-time assertion guard the arithmetic.
- [x] `AesGcmCipher.encrypt` rejects an IV that is not 12 bytes, matching java-sdk#393.
