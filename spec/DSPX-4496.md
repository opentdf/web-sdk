# Encapsulate AES-GCM IV generation in CryptoService; deterministic or RBG IVs per provider

## Summary

Route payload and metadata AES-GCM encryption through a per-key encryptor supplied by the
`CryptoService`. The encryptor owns its IV construction -- either the deterministic construction of
NIST SP 800-38D 8.2.1 or the RBG-based construction of 8.2.2 -- and reports which one, and its
invocation limit, as read-only properties. The SDK never supplies an IV; it only records the IV the
encryptor returns.

`DefaultCryptoService` uses the deterministic construction already built for #1018: a random 8-byte
fixed field, drawn once per encryptor, followed by a 4-byte big-endian invocation counter.

The decision record is the ADR "AES GCM i.v. Collision Risk" (DSPX-4492,
`adr/docs/decisions/dspx-4492-aes-gcm-iv-nonce-risk.md`), which accepts both constructions.

## Problem / Motivation

The writer used to draw a random 96-bit AES-GCM IV for every segment. At high segment counts, random
IVs accumulate collision risk according to the birthday bound. Repeating an IV with the same key
catastrophically compromises AES-GCM confidentiality and integrity.

Building deterministic IVs in the SDK fixes uniqueness within a TDF, but puts IV generation on the
wrong side of a cryptographic module boundary. Under FIPS 140-3 IG C.H, an IV that the caller
assembles and passes to a generic GCM encrypt is not an approved service, and the deterministic
counter state is itself a sensitive security parameter. A provider that wants IV generation inside
its boundary -- whether to use module-generated random IVs or a module-internal counter -- needs the
SDK to stop choosing IVs at all. The library should not need to know which kind of provider it has,
only what that provider guarantees.

## Proposed Solution

### Per-key encryptor SPI

Add an optional member to `CryptoService`:

```ts
createAesGcmEncryptor?: (key: SymmetricKey) => Promise<AesGcmEncryptor>;

interface AesGcmEncryptor {
  /** How this encryptor builds IVs. Final name TBD; see Open Questions. */
  readonly ivConstruction: 'deterministic' | 'rbg';
  /** Hard ceiling on `encrypt` calls, counting attempts rather than successes. */
  readonly invocationLimit: number;
  encrypt(plaintext: Uint8Array): Promise<{
    readonly iv: Uint8Array;
    ciphertext: Uint8Array;
    tag: Uint8Array;
  }>;
}
```

- No IV goes in; the IV only comes out. The SDK writes it to the segment prefix and to
  `encryptedMetadata.iv`, and never builds or picks one itself.
- The writer does not branch on provider identity. It uses `invocationLimit` to fail fast and
  `ivConstruction` only for diagnostics and documentation.
- The member is optional, like `generateMlKemKeyPair?`, so custom `CryptoService` implementations
  compiled against an older release still satisfy the type.

### Default provider: deterministic (8.2.1)

`DefaultCryptoService.createAesGcmEncryptor` wraps `GcmIvCounter`:

- The 8-byte fixed field is random, drawn once per encryptor through `randomBytes`.
- `ivConstruction` is `'deterministic'` and `invocationLimit` is 2^32.
- Invocations are consumed per attempt, so a retried encrypt never reuses an IV.

Drawing the fixed field per encryptor rather than per key is what makes the scheme safe:
`keyMiddleware` is a public option, so a caller may hand the same `KeyInfo` to two `encrypt` calls.
A constant fixed field -- including the all-zero one -- would then repeat the entire IV sequence,
metadata included, under an identical key.

### RBG providers (8.2.2)

A provider whose IVs come from an RBG inside its own boundary -- HSM or module backed, say --
reports `ivConstruction: 'rbg'`. Following the ADR, such a provider reports an `invocationLimit` of
at most 2^26 per key, which bounds the per-key collision probability at about 2^-45.

### Writer flow

- `writeStream` creates one encryptor per distinct key.
- With a single split, the metadata key is the payload key, so metadata is simply the first call on
  the payload encryptor. For the default provider that is invocation 0, and payload segments follow
  from invocation 1 -- byte-identical to #1018.
- With multiple splits, or when `keyMiddleware` returns a distinct manifest key, each split key gets
  its own encryptor for its metadata. Key access objects that share a split key draw successive IVs
  from that key's encryptor.
- Reaching `invocationLimit` throws `IvExhaustionError`, on known-length and unknown-length streams
  alike.
- A `CryptoService` without `createAesGcmEncryptor` falls back to an SDK-side encryptor built from
  `GcmIvCounter` and the existing caller-IV `encrypt`, so the writer has a single code path. For a
  single key access object this is byte-for-byte the #1018 layout. Such a provider gets IV
  uniqueness but not encapsulation.
- The writer wraps every encryptor, whether the provider's or the fallback, in a guard. The guard
  reads `invocationLimit` once, rejects limits outside 1..2^32, counts attempts, and refuses output
  that is not a 12-byte IV, a ciphertext as long as the plaintext, and a 16-byte tag.

### Segment sizing

Calculate AES-GCM segment overhead directly instead of encrypting and discarding a dummy segment. A
cipher-level test and a write-time assertion keep `encryptedPayloadSize` honest in the probe's
place; the assertion also checks that each encryptor result is a 12-byte IV, the ciphertext, and a
16-byte tag.

Raise the writer's `DEFAULT_SEGMENT_SIZE` (`client/builders.ts`) from 1 MiB to 2 MiB to match the
other SDKs. The reader's fallback for manifests that omit `encryptedSegmentSizeDefault` (`tdf.ts`)
stays at 1 MiB, so old files parse as before. At 2 MiB, a 2^26 limit still admits 128 TiB per key,
and a 50 TiB payload under RBG IVs has a collision probability of about 2^-47.7.

## Inputs / Outputs / Contracts

No wire-format or manifest schema changes. Each encrypted payload segment continues to store its
12-byte IV before the ciphertext and 16-byte authentication tag, and readers take every IV from the
segment prefix or the key access object, never recomputing it. TDFs written by either construction
read everywhere.

The TypeScript surface does move, all of it source compatible:

- `CryptoService.createAesGcmEncryptor?` and the `AesGcmEncryptor`, `AesGcmEncryptResult`, and
  `AesGcmIvConstruction` types are new.
- `SplitKey.write` and `SplitKey.getKeyAccessObjects` accept either the existing `Binary` metadata
  IV or a new `MetadataEncryptorSource`, which supplies an encryptor per split key.
- `SymmetricCipher.generateInitializationVector` and `SplitKey.generateIvBinary` still exist but are
  `@deprecated`; nothing in the SDK calls them and their output must not be used as a payload IV.
- `SymmetricCipher.encryptedPayloadSize(plaintextSize)` is new. It is concrete rather than
  `abstract`, throwing `ConfigurationError`, so a duck-typed cipher compiled against an older
  release still satisfies the class structurally.
- `SplitKey.encrypt`'s `ivBinary` parameter stays optional in the signature but now throws when
  omitted, rather than falling back to a random IV.
- `IvExhaustionError` is new and exported from the package root. It reports the limit of whichever
  encryptor, or fallback counter, was exhausted.

One behavior change is visible without code changes: callers that never set `windowSize` now get 2
MiB segments instead of 1 MiB.

Deliberate divergence from java-sdk#393, which uses an all-zero fixed field. The two are wire
compatible, so this is a writer-side hardening choice, not a format change. go-sdk already ships
both constructions. Worth raising with the BaseTDF spec owners.

## Edge Cases & Constraints

- Default provider:
  - Reusing a payload key across TDFs is safe for IV uniqueness, because each encryptor draws a
    fresh fixed field. It still means one key compromise exposes every TDF that shared it.
  - Carry propagates within the 32-bit invocation field only; the fixed field never changes.
  - Shortening the random part of the IV from 96 to 64 bits is a strict improvement _within_ a
    stream, and a small regression _across_ streams that share a key. With M total segments under
    random 96-bit IVs the collision probability was ~M^2/2^97; with N reused-key encrypts it is now
    ~N^2/2^65, and a fixed-field collision repeats the whole IV sequence rather than one segment. At
    N = 2^20 that is ~2^-25. Acceptable, but `keyMiddleware` makes key reuse a supported scenario,
    so it is a real tradeoff and not merely theoretical.
- RBG providers:
  - Uniqueness is probabilistic, ~k^2/2^97 for k invocations under one key.
  - A small explicit `windowSize` reaches the limit sooner: 16 KiB segments under a 2^26 limit cap
    the payload at 1 TiB.
  - Key reuse through `keyMiddleware` pools both TDFs' invocations under one birthday bound, and the
    per-encryptor limit cannot see across TDFs. Document it.
- Metadata:
  - Each key access object's metadata IV comes from its split key's encryptor, on the fallback path
    too. Two key access objects with the same `sid` therefore get distinct IVs, no longer relying on
    byte-identical metadata for safety.
  - Callers that invoke `SplitKey.write` directly with a `Binary` IV keep the old shared-IV
    behavior.
  - `method.iv` is vestigial and holds the first key access object's metadata IV.
- Empty payloads do not consume a payload invocation.
- `writeStream` rejects a non-positive or non-integer `segmentSizeDefault`. Previously
  `windowSize: 0` hung forever in the segmentation loop.

## Out of Scope

- Changing the BaseTDF wire format or validating deterministic IVs while reading.
- Non-payload AES-GCM operations such as EC/ML-KEM key wrapping, which use different keys. Moving
  them behind the same encapsulation is a follow-up ticket.
- Random-access or distributed segment writers; the web SDK writer emits segments sequentially.
- Reader-side validation of `segmentSizeDefault` against `encryptedSegmentSizeDefault`, including
  how to treat manifests that write those sizes as JSON strings. Tracked separately; it is a read
  path change with its own compatibility surface and does not belong with a writer fix.
- Cross-SDK IV-layout conformance vectors and RBG-IV cross-reads in xtest.
- ADR options D (per-segment-range key derivation) and E (deterministic generator inside a validated
  module). The encryptor SPI is the hook a provider would use to adopt E later.

## Acceptance Criteria

Delivered in #1018:

- [x] Every stream draws a fresh random fixed field through the injected crypto service.
- [x] Metadata encryption uses invocation 0 and payload segments begin at invocation 1.
- [x] Consecutive payload segments use consecutive invocations under one fixed field.
- [x] Two encrypts sharing a `KeyInfo` produce disjoint IVs, covered by regression test.
- [x] Counter carry and the 2^32 invocation ceiling are unit tested.
- [x] Segment-size calculation does not perform a throwaway encryption, and a cipher-level test plus
      a write-time assertion guard the arithmetic.
- [x] `AesGcmCipher.encrypt` rejects an IV that is not 12 bytes, matching java-sdk#393.

Encapsulation:

- [x] `CryptoService.createAesGcmEncryptor?` and `AesGcmEncryptor` exist; an IV cannot be passed in,
      and the returned `iv` is read-only.
- [x] `DefaultCryptoService` implements the encryptor with `GcmIvCounter`, and `writeStream` builds
      no IVs when the provider supplies an encryptor.
- [x] A spy RBG provider test shows metadata and every segment use provider-returned IVs, and the
      caller-IV `encrypt` is never invoked.
- [x] `invocationLimit` is enforced with `IvExhaustionError`, counting attempts, and tested with a
      low limit.
- [x] A provider without `createAesGcmEncryptor` falls back to the #1018 behavior, covered by test.
- [x] `DEFAULT_SEGMENT_SIZE` is 2 MiB, with docs and tests updated.

## Open Questions

- Final name and shape for the construction property: the `ivConstruction` enum, or a boolean such
  as `deterministicCounter` or `needsRbgIvs`.
- Whether to deprecate the SDK-side fallback once known custom providers implement the encryptor.
