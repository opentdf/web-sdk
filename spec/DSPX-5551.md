# range decrypt treats java trailing empty segment as uniform

## Summary
Plaintext range decrypt seeks directly on java-sdk TDFs whose plaintext is a
multiple of the segment size, instead of decrypting from segment 0.

## Problem / Motivation
java-sdk's writer (`TDF.java`, a `finished = nRead < 0` do-while) ends such a
plaintext with an empty segment: 28 bytes of IV and tag, `segmentSize: 0`.
`uniformSegmentSize` required the last segment's size to be in (0, S], so the
layout fell back to decrypting from the start. On a large file that reads
everything before the range; on a partially stored file (opentdf/tests#700) it
reads missing bytes and fails the segment hash check. A 64 MiB java TDF read in
segment 20 took 44 reads from byte 0; the go equivalent took 5.

## Proposed Solution
In `lib/tdf3/src/utils/plaintext-range.ts`, a layout is also uniform when every
segment but the last records size S and `encryptedSize(S)`, and the last records
0 and `encryptedSize(0)`. The segment before the empty one is the last data
segment: a range inside it also reads the one before it, and a range reaching
the end reads the empty segment.

## Inputs / Outputs / Contracts
No API change. `planPlaintextRange` returns fewer segments for these files.

## Edge Cases & Constraints
- java never writes a short segment followed by an empty one, so that stays
  non-uniform, as does an empty segment anywhere but last, or one whose
  ciphertext size is not `encryptedSize(0)`.
- DSPX-5219 guarantees hold: the plan still decrypts a non-last segment whose
  authenticated length must be S, and the end is confirmed by decrypting the
  empty segment, which is root-signed and must decrypt to 0 bytes.

## Out of Scope
Changing java-sdk to stop writing the empty segment; existing files need this
reader fix either way.

## Acceptance Criteria
- [x] java's exact-multiple layout plans only the covering segments.
- [x] A range reaching the end includes the empty segment.
- [x] Other zero-size placements remain non-uniform.
