# web-sdk: encrypt throughput — replace pure-JS CRC-32 and fix quadratic segment re-copy

## Summary
Found in the DSPX-5124 large-TDF runtime analysis (virtru-corp/adr docs/decisions/dspx-5124-analysis/runtime-limits-web.md), web-sdk main 59c42c894523, measured on Node 24.21.0.
ProblemsEncrypt is held back by a pure-JS CRC-32. Encrypt runs at about 400 MiB/s end to end, which is about 37 hours for 50 TiB. The CRC-32 alone runs at about 543 MiB/s. Decrypt, which needs no CRC, runs at about 5 GB/s.
Encrypt slows down quadratically as segment size grows. lib/tdf3/src/tdf.ts:665-683 re-copies the partial segment buffer on every input chunk. With 64 KiB input chunks:
16 MiB segments: 89 MiB/s, 1.8 GiB peak memory;
256 MiB segments: 5 MiB/s, 15.6 GiB peak memory.
This must be fixed before DSPX-4651 raises the default segment size.
Draft web-sdk #1021's ByteAccumulator does not fix this (confirmed in the 2026-10-18 audit). It replaces the segment-hash list, not the partial-segment re-copy loop. No open PR addresses either problem in this ticket.
These two problems are independent and have different fixes, so they can be split into separate tickets if they're worked separately.
Proposed fixUse a native or WASM CRC-32. Node has zlib.crc32 (Node ≥ 22.2), and browsers can use a WASM build. Alternatively, compute CRC only where the ZIP format requires it.
Accumulate segment bytes in preallocated buffers (or a list of chunks joined once per segment) instead of re-copying on every chunk.
Acceptance criteriaA throughput benchmark, in CI (see DSPX-4372) or as a documented script: encrypt reaches at least 1 GB/s in Node on reference hardware (target to be confirmed).
Encrypt throughput and peak memory are flat with respect to segment size, from 2 MiB to 256 MiB.

## Problem / Motivation
Encrypt is the slow direction of the web SDK, and it gets dramatically slower
as segments grow. Two independent causes:

1. **Quadratic re-buffering.** `writeStream` concatenated every input chunk
   onto the partial segment (`concatUint8([currentBuffer, value])`), and
   sliced the remainder off with another copy. Filling a segment of size S
   from chunks of size c copies about S²/2c bytes. Browser `File.stream()` and
   Node file streams deliver about 64 KiB chunks, so this bites at any segment
   size above the 2 MiB default, and DSPX-4651 needs larger segments to stay
   under the manifest string and heap limits.
2. **Pure-JS CRC-32.** ZIP needs a CRC-32 of every stored entry, so every
   output byte goes through `buffer-crc32.ts`, a byte-at-a-time table loop at
   about 500 MiB/s. That alone capped encrypt near 400 MiB/s.

## Proposed Solution
Two PRs, stacked, each independently correct:

1. **Segment buffer** (`DSPX-5232-segment-buffer`): copy each input byte once,
   into a segment-sized buffer allocated when a segment starts; queue full
   segments and encrypt them under the existing backpressure loop. Hand a full
   segment's buffer to the cipher without the extra `toArrayBuffer` copy, and
   drop a redundant copy in `AesGcmCipher.encrypt`. Adds
   `lib/scripts/bench-encrypt.mjs` (`npm run bench:encrypt`).
2. **CRC-32** (`DSPX-5232-crc`): use zlib's native `crc32` where the runtime
   has one (Node ≥ 20.15 / 22.2, Bun), reached through
   `process.getBuiltinModule('node:zlib')` so browser bundles never see a
   `node:zlib` import. Elsewhere use a slice-by-16 table loop.

## Inputs / Outputs / Contracts
- No public API change. `writeStream` output is byte-for-byte the same format;
  segment boundaries are unchanged.
- `tdf3/src/utils/buffer-crc32.ts` keeps `unsigned(buf, previous)` and adds
  `portableCrc32` and `crc32Backend: 'zlib' | 'portable'`.
- `npm run bench:encrypt -- [--lib DIR]... [--total 1GiB] [--chunk 64KiB]
  [--segments 2MiB,16MiB,64MiB,256MiB] [--json]`: one child process per
  segment size; reports encrypt MiB/s, peak RSS and the CRC-32 backend.

## Edge Cases & Constraints
- Empty input, input shorter than one segment, one-byte chunks, chunks that
  straddle boundaries, and one chunk holding several segments: covered by
  `tests/mocha/encrypt-segmentation.spec.ts`.
- A source that overwrites one buffer for every chunk is broken with any Web
  Streams consumer (the stream pulls again before the reader's `read()`
  continuation runs), so it is not supported, before or after.
- Peak memory cannot be literally flat in segment size: the cipher needs at
  least the plaintext and the ciphertext of one segment. It is now linear in S
  with a small constant instead of superlinear. The remaining per-segment
  copies (analysis item #10) are out of scope.
- `process.getBuiltinModule` is absent before Node 20.16 / 22.3; those
  runtimes, browsers, and Deno without Node compat use the portable CRC.

## Out of Scope
- The remaining per-segment copies in the cipher and crypto service.
- A CLI segment-size flag (analysis #17) and raising the default segment size
  (DSPX-4651).
- Removing the unused `buffer-crc32` npm dependency from `lib/package.json`.

## Acceptance Criteria
- [x] Documented throughput benchmark: `npm run bench:encrypt`.
- [x] Encrypt ≥ 1 GB/s in Node on reference hardware: 2.3-2.8 GB/s
  (M5 Pro, Node 24.21.0, 1 GiB in 64 KiB chunks).
- [x] Encrypt throughput flat from 2 MiB to 256 MiB segments.
- [x] Peak memory no longer superlinear in segment size (16.9 GiB → about
  3 GiB at 256 MiB).
