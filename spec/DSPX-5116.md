# web-sdk: plaintext byte-range decrypt in the SDK and @opentdf/ctl

## Summary
Part of DSPX-4886. Add plaintext-range decrypt to web-sdk and its CLI.
Current statelib/src/seekable.ts already has fromUrl, which reads remote TDFs with HTTP Range requests through the Chunker abstraction, so no separate range-loading ticket is needed for JS. What's missing is a decrypt option that limits output to a plaintext byte range. The decrypt path currently walks every segment.
SDK workAdd a plaintext range option to the decrypt API (for example { range: { offset, length } }). Map it to covering segments, fetch only those through the Chunker, verify each segment's hash, and trim the first and last segments.
Verify the root signature over the manifest's segment hashes before emitting plaintext.
Use number safely, or bigint where needed: offsets must work above 2^32, and Number.MAX_SAFE_INTEGER (about 8 PiB) is enough headroom. Validate inputs.
Prefetch must be bounded by the range, not the whole file. Related: DSPX-5075.
CLI interface (shared with the otdfctl and Java tickets)decrypt <file-or-url> --offset <N> --length <M>, with the same semantics: plaintext bytes, --length omitted means to EOF, an offset past EOF is an error. URL input goes through fromUrl.
Acceptance criteriaUnit tests cover: offset 0, a range inside one segment, a range crossing a segment boundary, the last short segment, length 0, offset at or past EOF, and offsets above 2^32 (with a mocked Chunker).
A counting Chunker asserts that only the tail, the manifest and the covering segments are read.
A tampered in-range segment fails. Range results match a full decrypt.
Related: DSPX-4648 (50 TiB gaps in web-sdk), DSPX-4653 (full-buffer traps in remote sources), DSPX-5075.

## Problem / Motivation
Reading a few bytes from the middle of a large TDF (seeking in media, sampling
a log, resuming a partial download) currently means decrypting every segment
from the start: `decryptStreamFrom` walks the whole segment list, and the CLI
has no way to ask for less. For remote TDFs, `fromUrl` can already issue HTTP
Range requests, so the only missing piece is a decrypt option that limits the
output, and the reads, to a plaintext byte range. Offsets must work past 4 GiB
(DSPX-4648), and prefetch must not run ahead of the range (DSPX-5075).

## Proposed Solution
- **Range option.** `range: { offset, length? }` on the decrypt API flows
  `ReadOptions` (`lib/src/opentdf.ts`) and `DecryptParams` /
  `DecryptParamsBuilder.withRange()` (`lib/tdf3/src/client/`) into
  `DecryptConfiguration.range` (`lib/tdf3/src/tdf.ts`). Semantics follow
  `Blob.slice` (see Edge Cases).
- **Planning.** `planPlaintextRange()` (`lib/tdf3/src/utils/plaintext-range.ts`)
  decides which segments to decrypt, how many plaintext bytes to drop before
  the range (`skip`), how many to return (`take`), and whether every decrypted
  segment must be length-checked (`checkLengths`). Positions are authenticated
  as described in the Security section:
  - *Uniform layout* (every segment but the last records plaintext size S and
    ciphertext size `cipher.encryptedPayloadSize(S)`; the last is in (0, S]):
    segment i starts at i * S, so the covering segments are found by division.
    If only the last segment covers the range, segment n-2 is read too, in the
    same ranged read, and its output dropped. Every decrypted segment's real
    plaintext length must equal its recorded size, otherwise `IntegrityError`.
  - *Any other layout* (allowed by the format; no SDK writer produces it):
    decrypt sequentially from segment 0 and drop output before the offset.
- **Fetch.** `decryptStreamFrom` builds the segment list and plans the range
  *before* the KAS rewrap, then passes only the planned segments to
  `prefetchSegmentBatches`. Prefetch is bounded by them, the batch size is
  capped at their number, and once `take` bytes have been handed out the batch
  stream is cancelled (so the fallback stops reading after the range too). Each
  segment is still checked against its root-signed hash.
- **Trim.** The output stream's `pull()` drops `skip` bytes (across as many
  segments as needed) and stops after `take` bytes, using `subarray` (no copies).
- **Order of checks.** The root signature over all segment hashes, and any
  assertions, are verified before the output stream is created, as for a full
  decrypt.
- **Errors.** `PlaintextRangeError` (`lib/src/errors.ts`, exported from
  `@opentdf/sdk`) extends `ConfigurationError`, for both a malformed range and
  an offset past the end. One class, because both are caller-input problems the
  caller fixes the same way, and the hierarchy's convention is a domain
  subclass of the broad category (as with `AttributeValidationError`).
  Subclassing keeps existing `instanceof ConfigurationError` checks working.
- **Fix.** `sliceAndDecrypt` located segments in a batch buffer with `%`, which
  is only right for batches starting at segment 0. It now subtracts the batch's
  first offset (separate `fix(sdk)` commit, with a regression test).
- **CLI.** `decrypt <file-or-url> --offset <N> --length <M>`. URLs become
  `{ type: 'remote' }` sources (`fromUrl`). Local files use the positioned-read
  `openFileChunker` from DSPX-5160 (#1089), which works past 4 GiB. A `PlaintextRangeError` prints its message and exits 1.

## Inputs / Outputs / Contracts
```ts
// @opentdf/sdk
type PlaintextRange = { offset: number; length?: number };
class PlaintextRangeError extends ConfigurationError {}
type ReadOptions = { /* ... */ range?: PlaintextRange };
// tdf3 Client
type DecryptParams = { /* ... */ range?: PlaintextRange };
DecryptParamsBuilder.withRange(offset: number, length?: number): DecryptParamsBuilder;
// internal
type DecryptConfiguration = { /* ... */ range?: PlaintextRange };
function validatePlaintextRange(range: PlaintextRange): void;
function planPlaintextRange<T extends { plainSegmentSize?: number; encryptedSegmentSize?: number }>(
  chunks: T[],
  range: PlaintextRange,
  encryptedSize: (plaintextSize: number) => number
): { chunks: T[]; skip: number; take: number; checkLengths: boolean };
```
- Output: a stream of exactly `min(length, plaintextSize - offset)` bytes.
- `offset`, `length`: non-negative safe integers (`Number.isSafeInteger`), so
  offsets up to `Number.MAX_SAFE_INTEGER` (about 8 PiB) work.
- Progress handler: cumulative ciphertext bytes of the segments read, including
  any read only to authenticate positions.
- CLI: `--offset <N>` and `--length <M>` are plain decimal integers (no sign,
  fraction, exponent or hex). `--length` alone starts at 0; `--offset` alone
  reads to the end. Errors exit with status 1.

## Edge Cases & Constraints
- `Blob.slice` semantics:
  - `offset <= plaintextSize` is valid. `offset == plaintextSize` gives empty
    output with no payload reads, whatever the length (including omitted).
  - `length` omitted reads to the end; a `length` running past the end is cut
    short; `length: 0` gives empty output with no payload reads.
  - An empty plaintext (n = 0 segments, or total size 0) with offset 0 gives
    empty output.
  - `offset > plaintextSize` throws `PlaintextRangeError`.
  - The otdfctl and Java range tickets (DSPX-5114, DSPX-5115) and the xtest
    cross-SDK tests (DSPX-5117) should use the same semantics.
- Invalid `offset` / `length` (negative, fractional, NaN, infinite, unsafe)
  throws `PlaintextRangeError`, from the builder and again from the decrypt.
- The plaintext size for these checks is the sum of the recorded sizes. When
  nothing is read (offset at the end, length 0), it is not verified.
- Any segment without a usable plaintext size (missing size and no
  `segmentSizeDefault`, negative, or a total past `MAX_SAFE_INTEGER`) makes the
  range unmappable: `InvalidFileError`.
- All of the above are raised before the KAS rewrap (the empty-output cases
  still rewrap and verify the root signature).
- A tampered segment that is read fails the read (`IntegrityError` on a hash
  mismatch, `DecryptError` on an AEAD failure). As in #1092, the batch fails as
  a whole, so no plaintext from a batch containing a bad segment is emitted.
- Non-uniform layouts read from segment 0, so they cost as much as a full
  decrypt up to the end of the range.

## Security: authenticating plaintext positions
Threat model: an attacker without the key can edit both the manifest and the
payload bytes, but not the segment hash list, which the root signature covers.
So the segment count n, and each segment's exact ciphertext (and therefore its
length, once its hash is checked), are authenticated. The recorded sizes of
segments that are never read are not.

- Summing recorded plaintext sizes is unsound: shrinking segment 0's recorded
  size moves every later authentic segment to a smaller offset.
- Deriving positions from ciphertext offsets is also unsound: inflating
  segment 0's recorded sizes and inserting matching junk into the payload
  leaves every later segment passing its hash check at a shifted offset.

The rule implemented:
- In a uniform layout, segment i starts at i * S. S comes from the manifest, so
  the read always decrypts at least one non-last segment, whose authenticated
  length must equal S (segment n-2 is added when only the last segment covers
  the range; with n = 1 there is nothing to confirm, as the start is 0). Every
  decrypted segment's length must equal its recorded size, which for the last
  segment is total - (n-1) * S.
- Any other layout is decrypted from segment 0, so positions come from the
  authenticated plaintext itself.

Tests reproduce the attacks (shrinking an earlier segment; inflating it and
padding the payload; relabelling the layout with another uniform size). Each
range read either fails or returns the correct bytes, never a different
authentic segment.

Residual assumption: the file's *authentic* layout is uniform whenever its
manifest claims so. If a key holder wrote segments of differing sizes, a
keyless editor could relabel the manifest as uniform; the covering segments
and one non-last segment would pass their length checks, but unread earlier
segments would not be checked. No SDK writer produces such files; closing this
fully would need the format to bind segment sizes into the root signature.

## Out of Scope
- Changing the TDF format to bind segment sizes into the root signature.
- Random access APIs beyond a single contiguous range per decrypt (for example,
  multiple ranges or a seekable reader).
- Legacy (non-ZTDF) container formats.

## Acceptance Criteria
- [x] Unit tests: offset 0; a range inside one segment; across a segment
  boundary; the last short segment; length 0; offset at EOF (empty) and past EOF
  (`PlaintextRangeError`); empty plaintext
  (`lib/tests/mocha/decrypt-range.spec.ts`, `lib/tests/mocha/unit/plaintext-range.spec.ts`).
- [x] Offsets above 2^32 through a mocked chunker: a sparse archive whose
  payload starts with a 4097 MiB hole that must never be read.
- [x] A counting chunker shows only format sniffing, the zip tail, central
  directory and local headers, the manifest, and the planned payload span are
  read; a range in the last segment also reads segment n-2.
- [x] A tampered in-range segment fails; a tampered out-of-range segment is not read.
- [x] The root signature is still verified for a range read.
- [x] Manifest and payload edits cannot move an authentic segment to another offset.
- [x] A non-uniform layout falls back to decrypting from segment 0, returns the
  right bytes, and stops reading after the range.
- [x] Range results match the same slice of a full decrypt.
- [x] `sliceAndDecrypt` regression test for spans not starting at segment 0.
- [x] CLI: `--offset` / `--length` parsing, URL and local file sources, and
  range errors as CLI errors
  (`cli/tests/source.spec.ts`, `cli/bin/opentdf.bats`).
