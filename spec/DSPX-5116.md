# web-sdk: plaintext byte-range decrypt in the SDK and @opentdf/ctl

## Summary
Part of DSPX-4886. Add plaintext-range decrypt to web-sdk and its CLI.
Current statelib/src/seekable.ts already has fromUrl, which reads remote TDFs with HTTP Range requests through the Chunker abstraction, so no separate range-loading ticket is needed for JS. What's missing is a decrypt option that limits output to a plaintext byte range. The decrypt path currently walks every segment.
SDK workAdd a plaintext range option to the decrypt API (for example { range: { offset, length } }). Map it to covering segments, fetch only those through the Chunker, verify each segment's hash, and trim the first and last segments.
Verify the root signature over the manifest's segment hashes before emitting plaintext.
Use number safely, or bigint where needed: offsets must work above 2^32, and Number.MAX_SAFE_INTEGER (about 8 PiB) is enough headroom. Validate inputs.
Prefetch must be bounded by the range, not the whole file. Related: DSPX-5075.
CLI interface (shared with the otdfctl and Java tickets)decrypt <file-or-url> --offset <N> --length <M>, with the same semantics: plaintext bytes, --length omitted means to EOF, an offset past EOF is an error. URL input goes through fromUrl.
Acceptance criteriaUnit tests cover: offset 0, a range inside one segment, a range crossing a segment boundary, the last short segment, length 0, offset at or past EOF, and offsets above 2^32 (with a mocked Chunker).
A counting Chunker asserts that only the tail, the manifest and the covering segments are read.
A tampered in-range segment fails. Range results match a full decrypt.
Related: DSPX-4648 (50 TiB gaps in web-sdk), DSPX-4653 (full-buffer traps in remote sources), DSPX-5075.

## Problem / Motivation
Reading a few bytes from the middle of a large TDF (seeking in media, sampling
a log, resuming a partial download) currently means decrypting every segment
from the start: `decryptStreamFrom` walks the whole segment list, and the CLI
has no way to ask for less. For remote TDFs, `fromUrl` can already issue HTTP
Range requests, so the only missing piece is a decrypt option that limits the
output, and the reads, to a plaintext byte range. Offsets must work past 4 GiB
(DSPX-4648), and prefetch must not run ahead of the range (DSPX-5075).

## Proposed Solution
- **Range option.** `range: { offset, length? }` on the decrypt API flows
  `ReadOptions` (`lib/src/opentdf.ts`) and `DecryptParams` /
  `DecryptParamsBuilder.withRange()` (`lib/tdf3/src/client/`) into
  `DecryptConfiguration.range` (`lib/tdf3/src/tdf.ts`).
- **Mapping.** `plaintextRangeChunks()` (`lib/tdf3/src/utils/plaintext-range.ts`)
  builds a running total of each segment's plaintext size (`segmentSize`,
  falling back to `segmentSizeDefault`) and binary-searches it for the first
  and last covering segments. It returns those segments, the bytes to drop from
  the front of the first, and the total bytes to return.
- **Fetch.** `decryptStreamFrom` builds the segment list and maps the range
  *before* the KAS rewrap, then passes only the covering segments to
  `prefetchSegmentBatches`. Prefetch is therefore bounded by the range, and the
  batch size is capped at the number of covering segments. Each segment is still
  read with one ranged read per batch and checked against its hash.
- **Trim.** The output stream's `pull()` drops `skip` bytes from the first
  segment and stops after `take` bytes, using `subarray` (no copies).
- **Order of checks.** The root signature over all segment hashes, and any
  assertions, are verified before the output stream is created, as for a full
  decrypt.
- **Fix.** `sliceAndDecrypt` located segments in a batch buffer with `%`, which
  is only right for batches starting at segment 0. It now subtracts the batch's
  first offset (separate `fix(sdk)` commit, with a regression test).
- **CLI.** `decrypt <file-or-url> --offset <N> --length <M>`. URLs become
  `{ type: 'remote' }` sources (`fromUrl`). Local files are read with positioned
  reads on a file handle instead of `fs.openAsBlob`, whose `size` wraps at
  4 GiB on Node 24.21.

## Inputs / Outputs / Contracts
```ts
// lib/tdf3/src/utils/plaintext-range.ts (also exported from @opentdf/sdk)
type PlaintextRange = { offset: number; length?: number };

// @opentdf/sdk
type ReadOptions = { /* ... */ range?: PlaintextRange };
// tdf3 Client
type DecryptParams = { /* ... */ range?: PlaintextRange };
DecryptParamsBuilder.withRange(offset: number, length?: number): DecryptParamsBuilder;
// internal
type DecryptConfiguration = { /* ... */ range?: PlaintextRange };
function validatePlaintextRange(range: PlaintextRange): void;
function plaintextRangeChunks<T extends { plainSegmentSize?: number }>(
  chunks: T[],
  range: PlaintextRange
): { chunks: T[]; skip: number; take: number };
```
- Output: a stream of exactly `min(length, plaintextSize - offset)` bytes.
- `offset`, `length`: non-negative safe integers (`Number.isSafeInteger`), so
  offsets up to `Number.MAX_SAFE_INTEGER` (about 8 PiB) work.
- Progress handler: cumulative ciphertext bytes of the covering segments read.
- CLI: `--offset <N>` and `--length <M>` are plain decimal integers (no sign,
  fraction, exponent or hex). `--length` alone starts at 0; `--offset` alone
  reads to the end. Errors exit with status 1.

## Edge Cases & Constraints
- `length` omitted: read to the end. `length` running past the end: cut short.
- `length: 0`: empty output, no payload reads (the manifest and root signature
  are still checked, and the KAS rewrap still happens).
- `offset >= plaintextSize` is a `ConfigurationError`, even with `length: 0`, and
  so is every range on an empty plaintext.
- Invalid `offset` / `length` (negative, fractional, NaN, infinite, unsafe) is a
  `ConfigurationError`, raised by the builder and again by the decrypt.
- Any segment without a usable plaintext size (missing size and no
  `segmentSizeDefault`, negative, or a total past `MAX_SAFE_INTEGER`) makes the
  range unmappable: `InvalidFileError`. An empty (size 0) segment *inside* the
  range is also refused, since decryption only length-checks segments with a
  nonzero recorded size.
- All of the above are raised before the KAS rewrap.
- Segments may vary in size; the last is usually short.
- A tampered covering segment fails the read (`IntegrityError` on a hash
  mismatch, `DecryptError` on an AEAD failure). As in #1092, the batch fails as
  a whole, so no plaintext from a batch containing a bad segment is emitted.
- **Security note.** The root signature covers the ordered segment hashes but
  not the segment sizes. A range read checks that each returned segment is the
  authentic segment *i* and has its recorded length, but the plaintext offset of
  segment *i* is the sum of the *recorded* sizes of segments before it, which a
  range read does not verify. A manifest editor without the key cannot forge
  plaintext, but could shift which authentic segment a given offset maps to. A
  full decrypt checks every size.

## Out of Scope
- Changing the TDF format to bind segment sizes into the root signature.
- `fs.openAsBlob` for **encrypt** inputs over 4 GiB in the CLI (decrypt and
  inspect no longer use it).
- Random access APIs beyond a single contiguous range per decrypt (for example,
  multiple ranges or a seekable reader).
- Legacy (non-ZTDF) container formats.

## Acceptance Criteria
- [x] Unit tests: offset 0; a range inside one segment; across a segment
  boundary; the last short segment; length 0; offset at and past EOF
  (`lib/tests/mocha/decrypt-range.spec.ts`, `lib/tests/mocha/unit/plaintext-range.spec.ts`).
- [x] Offsets above 2^32 through a mocked chunker: a sparse archive whose
  payload starts with a 4097 MiB hole that must never be read.
- [x] A counting chunker shows only format sniffing, the zip tail, central
  directory and local headers, the manifest, and the covering payload span are read.
- [x] A tampered in-range segment fails; a tampered out-of-range segment is not read.
- [x] The root signature is still verified for a range read.
- [x] Range results match the same slice of a full decrypt.
- [x] `sliceAndDecrypt` regression test for spans not starting at segment 0.
- [x] CLI: `--offset` / `--length` parsing, URL and local file sources, and
  positioned reads past 4 GiB (`cli/tests/source.spec.ts`, `cli/bin/opentdf.bats`).
