# Modernize the TypeScript + ESLint toolchain across web-sdk

## Summary

Make linting reproducible across `lib/`, `cli/`, and `web-app/`, adopt native flat configs and typed
rules, and enable strict SDK compilation while preserving its public behavior and
ESM/CommonJS/declaration outputs. Upgrade TypeScript through separate 5.9 and 6.x stages; evaluate
TypeScript 7 in a follow-up.

Implementation and validation were delegated to five `gpt-5.6-luna` sub-agents, with the coordinator
owning version decisions, compatibility review, integration, and final gates. The result retains
TypeScript 5.9.3 for the landing change; an isolated TypeScript 6.0.3 compiler probe is green and
remains suitable for the separate Stage 4 PR.

## Problem / Motivation

None of the three packages declares ESLint directly. Their lockfiles resolve three different ESLint
majors, and their configs depend on `FlatCompat` and undeclared imports. Typed rules are absent
despite TypeScript project configuration. The SDK enables only a partial set of strict checks and
disables property initialization checks. CLI compilation inherits SDK declaration-output paths.

These versions come from manifests and lockfiles inspected on 2026-09-22, not from installed
dependencies. They correct the original draft's version table.

| Tool                        | `lib/`   | `cli/`   | `web-app/` |
| --------------------------- | -------- | -------- | ---------- |
| TypeScript, declared        | `^5.8.2` | `^5.8.2` | `^5.8.3`   |
| TypeScript, locked          | `5.8.2`  | `5.9.3`  | `5.8.3`    |
| ESLint, locked              | `8.57.1` | `10.0.3` | `9.39.2`   |
| `@eslint/js`, locked        | `9.26.0` | `9.39.4` | `9.39.2`   |
| `typescript-eslint`, locked | `8.54.0` | `8.57.0` | `8.26.0`   |
| Prettier, locked            | `3.5.3`  | `3.8.1`  | `3.8.1`    |

Repository findings that affect the plan:

- `.nvmrc` and CI use Node 24; `AGENTS.md` says Node 22. `CLAUDE.md` links to `AGENTS.md`, so only
  the target file needs editing.
- CLI's inherited `declarationDir` resolves into `lib/dist/types`.
- `web-app/tsconfig.node.json` combines `module: ESNext` with `moduleResolution: node16`; validate
  and correct that referenced configuration.
- `make test` covers the three main packages, not the separate Playwright project.
- Instrumented app tests alias SDK TypeScript sources, so they do not alone prove the packed SDK
  works for consumers.

## Proposed Solution

### Dependencies and flat configs

Pin the same exact direct versions of ESLint 10.x, `@eslint/js` 10.x, `typescript-eslint` 8.70 or
newer within 8.x, and compatible stable Prettier 3.x across the three packages. Select exact patches
after checking registry availability, engines, and peers; do not copy unverified "latest" numbers
from the original draft. Regenerate each affected lockfile without unrelated upgrades.

Node 24 is the development/CI baseline. ESLint 10 supports Node 24; current TypeScript ESLint
guidance supports ESLint 10 and TypeScript below 6.1. Verify the chosen versions, Chai/Prettier
plugins, and TypeDoc together; do not force an incompatible peer graph.
[ESLint migration guidance](https://eslint.org/docs/latest/use/migrate-to-10.0.0),
[typescript-eslint compatibility](https://typescript-eslint.io/users/dependency-versions/).

Use `defineConfig` from `eslint/config`, native TypeScript presets, `tseslint.parser`, and
`eslint-plugin-prettier/recommended`. This updates the draft's proposed helper: `tseslint.config()`
is deprecated. Declare every imported third-party package directly, including `globals`; Node
built-ins need no entry. Remove direct `@eslint/eslintrc` dependencies and obsolete direct
parser/plugin dependencies if the umbrella package replaces those imports.
[Configuration guidance](https://typescript-eslint.io/packages/typescript-eslint/).

Enable `recommendedTypeChecked` for maintained TypeScript sources and existing tests in each
package's lint scope. Use `ecmaVersion: 'latest'`, `sourceType: 'module'`, `projectService: true`,
and a package-local `tsconfigRootDir`. Remove recursive `parserOptions.project` globs. Scope
browser, Node, and test globals to their actual files. Quote recursive CLI lint globs so ESLint
selects nested files consistently across shells.

Project service does not automatically admit files outside a TypeScript project. Ensure every
typed-linted file belongs to an appropriate project. Use untyped overrides for standalone JavaScript
tooling; reserve `allowDefaultProject` for specific justified config files. Do not use recursive
catch-all patterns or expand Playwright's lint scope without providing its own project
configuration. [Parser project-service guidance](https://typescript-eslint.io/packages/parser/).

Scope Chai's replacement expression rule to assertion tests. Audit the existing blanket test
`ban-ts-comment` exception; prefer typed fixtures and intentional `@ts-expect-error` cases. Add
narrow ESLint ignores for `lib/src/platform/**` and `lib/tdf3/src/crypto/jose/vendor/**`, matching
existing generated/vendor formatting boundaries. These files remain in the compiler graph: lint
ignores do not exempt them from strictness or `noUnusedParameters`. Fix generators/integration
points when needed, rather than hand-editing generated files or excluding maintained SDK code.
Record any additional deferred diagnostic as a follow-up.

### Compiler configuration

Land one exact TypeScript 5.9.x version first. Remove unused `baseUrl`, separate CLI output settings
from SDK settings, and validate the app's referenced Node config. A small root `tsconfig.base.json`
may hold shared checks; package configs must own `include`, `rootDir`, emit/declaration paths,
module settings, target, and ambient types. CLI emits to `cli/dist` and must not write declarations
into the SDK; the CLI package has no published declaration contract.

Enable SDK `strict: true`, `noUnusedParameters`, `noFallthroughCasesInSwitch`, and
`verbatimModuleSyntax`. Remove redundant strict-subset flags while retaining additional checks such
as `noImplicitReturns`, `noImplicitOverride`, and `noUnusedLocals`. Fix property initialization and
narrow unknown caught values rather than adding blanket casts or global strictness opt-outs.

Set `verbatimModuleSyntax: false` explicitly in `lib/tsconfig.commonjs.json`, with a comment
explaining that this pass transforms the same ESM sources into CommonJS. The flag otherwise prevents
that transformation. Preserve both compiler passes, package type boundaries including
`lib/tests/package.json`, and `scripts/add-module-types.sh`.
[TypeScript module-syntax behavior](https://www.typescriptlang.org/tsconfig/verbatimModuleSyntax.html).

Determine target/lib from the supported consumer runtime matrix, not `.nvmrc` alone. ES2022 is a
candidate SDK/CLI target, subject to browser and Node minimums and class-field emit review. Retain
SDK ES2021 and record a follow-up if a higher floor cannot be justified. Preserve explicit
class-field semantics if a target change would otherwise alter initialization. Keep the app's module
settings appropriate to its Vite bundler.

TypeScript 5.9 changes typed-array and DOM relationships. Check WebCrypto `BufferSource`,
`ArrayBuffer`, Node `Buffer`, and views carefully: preserve offsets and lengths rather than hiding
errors with double casts.
[TypeScript 5.9 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-9.html).

Run TypeScript 6 migration only after 5.9 and strictness pass. Audit changed `types`/`rootDir`
defaults, deprecated options, and CommonJS resolution. Do not silence deprecations globally. If
preserving the dual build requires a larger redesign, keep the green 5.9 result and record a linked
6.x follow-up with exact reproduction steps.
[TypeScript 6 migration notes](https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/).

## Implementation Sequence and Delegation

Use `gpt-5.6-luna` agents for implementation and testing. The coordinator owns version decisions,
cross-package contracts, review, integration, and this spec. Allow at most three sub-agents
alongside the coordinator.

| Role                 | File/task ownership                                                                | Handoff                                                                              |
| -------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| SDK implementer      | `lib/` configs, manifest/lockfile, maintained SDK sources/tests, SDK build helpers | Changed files, diagnostics resolved, public-type/runtime changes, focused checks     |
| Consumer implementer | `cli/` and `web-app/` configs, manifests/lockfiles, source fixes                   | Builds/lint against the agreed SDK contract and versions                             |
| Independent tester   | Baseline capture, package-contract checks, test execution, evidence                | Commands, exit status, coverage, declaration/export differences, unresolved failures |

Assign shared files (`tsconfig.base.json`, `AGENTS.md`, Makefile, CI) to one implementer at a time.
Split SDK fixes further only when diagnostics identify disjoint file sets. Never let agents rewrite
the same lockfile concurrently. Serialize installs, builds, formatting, and tests that mutate shared
SDK artifacts or use the same ports. The tester can prepare checks while implementers edit, but runs
acceptance against a stable handoff. Use separate workspaces for concurrent baseline/final execution
if needed. Test failures return to the implementer; the tester must not weaken rules, coverage, or
assertions to obtain a pass.

### Stage 0: Baseline and version decisions

Owner: independent tester, reviewed by coordinator.

1. Record revision, Node/npm versions, manifests/lockfiles, and installed tool versions. Verify
   candidates with `npm view <package>@<candidate> version engines peerDependencies --json`.
2. Run `make ci` from the repo root: the SDK tarball must exist before fresh CLI/app dependency
   installs. Inspect any manifest/lockfile changes made by the Makefile's install workflow.
3. Capture package lint results/timings, builds, and existing test failures. Save each effective
   `tsc --showConfig`, including SDK CommonJS and app Node configs.
4. Archive the SDK tarball, packed file list, export map, and `dist/web`, `dist/cjs`, and
   `dist/types` outside build-cleaned directories.
5. Agree on exact versions, runtime-target policy, and generated-code boundaries. Investigate
   baseline failures separately from modernization regressions.

Exit: reproducible evidence and compatible versions. Missing dependencies or services produce a
blocked/failed check, never an assumed pass.

### Stage 1 / PR 1: Reproducible native typed linting

Owners: SDK and consumer implementers on disjoint package files; tester validates.

1. Pin lint/format tools, declare missing imports, remove compatibility dependencies, and rewrite
   all three configs using the policy above.
2. Fix typed-rule findings by package and rule. Separate mechanical fixes and formatting from
   changes to promises, error handling, or runtime validation.
3. Replace broad test exceptions where possible. For unavoidable suppressions, use the smallest
   scope, explain why, and link a real follow-up ticket here. Disabling whole typed-rule families is
   not an acceptable landing strategy.
4. Correct the Node version in `AGENTS.md`. Check TSX parsing, Chai assertions, direct config
   imports, typed-rule execution, and package lint commands.

Exit: `make lint` passes; all three packages resolve the selected ESLint version without invalid
peers. Changed behavior has focused regression coverage and passes affected suites. Record
package-level lint time before/after, excluding installation time. If the baseline compatibility
probe shows that typed lint requires 5.9, promote Stage 2's compiler-only upgrade into a
prerequisite PR before PR 1. Stage 2 then owns the remaining config cleanup; do not combine
strictness churn with the prerequisite.

### Stage 2 / PR 2: TypeScript 5.9 and configuration ownership

Owners: SDK implementer for shared config/build; consumer implementer for adoption.

1. Pin one 5.9.x compiler. Align Node types with the supported tool/runtime baseline; audit the
   app's current `@types/node` 26.x dependency.
2. Remove `baseUrl`, isolate package emit paths, fix CLI declaration inheritance, and validate app
   Node/bundler configurations.
3. Fix compiler diagnostics, especially binary/WebCrypto boundaries. Add focused offset/length or
   error-path tests for behavior changes.
4. Apply target/lib changes only with consumer-runtime evidence.

Exit: all package builds and packed-consumer checks pass. Review SDK ESM/CJS and public declaration
diffs. Verify CLI builds cannot alter SDK declaration output.

### Stage 3 / PR 3: Strict SDK and explicit module syntax

Owners: SDK implementer, then consumer implementer for downstream type fixes.

1. Enable required flags and the documented CommonJS override. Convert type-only imports/exports
   while preserving intentional side effects.
2. Fix bounded diagnostic groups: property initialization, caught errors, unused parameters,
   fallthrough, and remaining typed boundaries. Establish lifecycle invariants before using
   definite-assignment assertions.
3. Classify declaration changes as compatible clarification, accidental inference drift, or API
   changes. Preserve intended signatures with explicit annotations; escalate breaking public-type or
   crypto behavior changes to the coordinator.
4. Rebuild/repack before testing consumers. Do not hand-edit generator output.

Exit: all required gates below pass, with no unexplained type/runtime changes. Every newly
suppressed rule has a linked follow-up.

### Stage 4 / separate PR: TypeScript 6 readiness

Owner: SDK implementer for a bounded probe; consumers/tester follow once viable.

Upgrade to a verified compatible 6.x patch, resolve deprecations/default changes, and repeat
compiler, package-contract, lint, and functional gates. Verify TypeDoc and parser compatibility too.
Land separately if green; otherwise record exact blockers and a linked follow-up while retaining
5.9. TypeScript 7/tsgo remains a separate evaluation.

## Inputs / Outputs / Contracts

- No intended changes to SDK APIs, CLI flags, TDF wire formats, cryptography, or authentication
  behavior. Identify and test compiler-driven runtime fixes.
- Preserve `dist/web`, `dist/cjs`, `dist/types`, module markers, declaration maps, and packaged
  source layout. Inspect declarations after both compiler passes, which currently share a
  declaration output directory.
- Preserve `main`, `types`, and export conditions for `.`, `./singlecontainer`, `./assertions`,
  `./encodings`, `./cryptoutils`, `./platform`, and concrete `./platform/*` paths. Do not silently
  redesign legacy metadata differences.
- No repository config may use `FlatCompat` or import `@eslint/eslintrc`. A transitive lockfile
  entry is allowed if another dependency still needs it.

## Validation Plan

The independent tester runs focused checks at each handoff and complete gates after integration.
Repeat checks after relevant changes, not after docs-only edits.

| Check                 | Commands / evidence                                                                                                                                                   |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dependencies          | In each package: `npm ls eslint @eslint/js typescript-eslint typescript prettier`; inspect direct dependencies and full ESLint graph                                  |
| Effective lint config | Package-local `npx --no-install eslint --print-config <file>` for SDK source/test, CLI source/test, and app TSX                                                       |
| Typed-rule execution  | Temporary in-project fixture with an unhandled promise must report `no-floating-promises`; remove after checking                                                      |
| Lint/build            | Each package's `npm run lint` and `npm run build`; explicitly validate the app Node tsconfig too                                                                      |
| Dual SDK emit         | Verify effective ESM `verbatimModuleSyntax: true` and CJS `false`; execute both passes through the SDK build and inspect final declarations in the intended directory |
| Declarations          | Baseline/final `dist/types` diff; review signatures/nullability separately from maps and path noise                                                                   |
| SDK suites            | `cd lib && npm test`: Mocha, Web Test Runner, Karma/ChromeHeadless, coverage merge                                                                                    |
| CLI suites            | `cd cli && npm test`; `bats bin/opentdf.bats` with CI's Bats helpers                                                                                                  |
| App suites            | `cd web-app && CI=true npm test`; verify browser-driven tests and coverage artifacts                                                                                  |
| Final repo gates      | `make lint`, `CI=true make test`, and `make license-check`, serialized                                                                                                |
| Formatting            | Pinned Prettier `--check` on changed supported files, respecting generated-file ignores                                                                               |

SDK browser suites require a working Chrome/Chromium installation and any needed Karma `CHROME_BIN`
configuration. The app's Vitest suite launches Playwright Chromium too: install its browser from
`web-app/` with `npx --no-install playwright install chromium` before running app tests, including
via `make test`. Linux runners also need the browser system dependencies used in CI. The separate
roundtrip harness installs its own three-browser prerequisites.

For the package-contract gate, pack the SDK and install the tarball in a temporary consumer.
Recursively verify all exported condition targets in the archive and enumerate actual `platform/*`
files. Load every named entry point using both ESM imports and CommonJS requires, plus
representative wildcard modules. Compile `.mts`/`.cts` NodeNext consumers and a bundler-resolution
consumer with declaration checking enabled. Check both the chosen compiler and the oldest documented
consumer compiler; use the existing 5.8 baseline if no minimum is documented. Compare against
baseline interop failures. Build the app without `COVERAGE` as well, so it consumes the tarball
instead of source aliases.

Preserve SDK merged coverage thresholds: 75% lines, 75% statements, 70% branches, and 65% functions.
Preserve WTR's 65% statements, 60% branches, and 50% functions thresholds. The app produces coverage
reports without its own numeric gate; those reports do not substitute for SDK threshold enforcement.

### Separate Playwright gate

Follow the platform-roundtrip recipe in `.github/workflows/reusable_build-and-test.yaml`.
Prerequisites: SDK and CLI tarballs (`make cli` builds the latter), Docker/Compose, CI-compatible
platform checkout and Go toolchain, test identity-provider/KAS setup, browsers, and free service
ports. Record the backend revision. With these in place, run from `.github/workflows/roundtrip`:

```sh
docker compose up -d --wait --wait-timeout 240
CI=true PLAYWRIGHT_TESTS_TO_RUN=roundtrip ./wait-and-test.sh platform
```

The harness configures platform and Vite, installs the browser-test dependencies, runs CLI
roundtrips and Playwright, and checks browser coverage collection. Playwright covers Chromium,
Firefox, and WebKit. A standalone `cd web-app/tests && npm test` requires those services already
running; `make test` does not supply this gate. Run the opt-in `huge` suite for changes to
binary/streaming behavior, rather than every config edit. Clean up test services and processes after
validation.

## Edge Cases & Constraints

- Initialization fixes, error narrowing, and promise handling can change behavior; a compiler/lint
  origin does not make them automatically mechanical.
- Type-only import conversion can remove side effects. Target changes can alter class-field emit.
  Ambient API declarations do not supply runtime polyfills.
- Typed linting may slow CI. Record comparable wall time and investigate project
  discovery/default-project overhead without disabling typed checks.
- Builds and Makefile commands overwrite artifacts and can update dependency metadata. Preserve
  baseline evidence and serialize shared-workspace validation.
- PR descriptions must call out the published SDK's declaration/build and auth/crypto risk, with
  concrete validation evidence.

## Out of Scope

- TypeScript 7/tsgo adoption, bundler replacement, or SDK packaging redesign.
- Mandatory `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, or `erasableSyntaxOnly`;
  measure and propose focused follow-ups if useful.
- Unrelated repository-wide formatting or hand-maintained generated/vendor code.
- Publishing releases or changing consumer runtime policy without evidence.
